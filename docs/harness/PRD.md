# PRD: 집중하면 레벨업 Spring Boot 서버 리뉴얼

마지막 갱신: 2026-05-28

## 1. What

집중하면 레벨업 서버는 사용자의 집중 기록, 목표, 보상, 랭킹, 길드, 결제, 관리자 운영 기능을 처리하는 Spring Boot 기반 백엔드 서버다.

이번 리뉴얼의 목표는 기존 기능을 안정화하고, API/Admin/Batch를 독립 실행 가능한 멀티모듈 구조로 정리하여 장기 운영 가능한 서버로 만드는 것이다.

## 2. Why

### 현재 문제

- API, Admin, Batch의 실행 책임과 배포 단위가 아직 완전히 정리되지 않았다.
- 집중 시간 저장, 보상 지급, 랭킹 정산처럼 중복 요청과 동시성에 민감한 기능이 존재한다.
- 기존 기능은 많지만, 서버 작업 기준 문서와 진행 기록이 부족하다.
- 운영자/CS 기능과 사용자 API 기능이 장기적으로 더 명확히 분리될 필요가 있다.

### 기대 효과

- AI 작업자와 개발자가 같은 기준으로 서버 작업을 진행할 수 있다.
- API/Admin/Batch를 각각 독립적으로 검증하고 실행할 수 있다.
- 집중 시간, 보상, 랭킹, 결제 같은 고위험 기능의 정합성을 개선할 수 있다.
- 향후 운영, 배포, 장애 대응, 기능 확장이 쉬워진다.

## 3. Who

### 주요 사용자

- 모바일 앱 사용자
  - 집중 시간을 기록하고, 보상과 랭킹을 확인하는 실제 서비스 사용자

### 보조 사용자

- 운영자/CS 담당자
  - 유저 조회, 신고 확인, 재화 지급, 랭킹 경고, 길드 정보 수정 등을 수행한다.

### 개발/운영 사용자

- 서버 개발자와 AI 에이전트
  - PRD, Architecture, Progress, Decisions 문서를 기준으로 기능 구현과 리팩터링을 수행한다.

## 4. Scope

### 이번 리뉴얼에 포함

- [ ] API/Admin/Batch 멀티모듈 구조 정리
- [ ] 각 모듈의 Gradle 의존성 및 실행 방식 검증
- [ ] 현재 인프라 구조와 목표 인프라 구조 문서화
- [ ] 집중 시간 저장 로직 분석 및 안정화 설계
- [ ] 보상, 랭킹, 결제 흐름의 중복 처리 위험 점검
- [ ] 관리자/CS 기능의 책임 범위 정리
- [ ] 하네스 문서와 에이전트 작업 규칙 정리

### 이번 리뉴얼에 포함하지 않음

- [ ] 모바일 앱 UI 구현
- [ ] 캐릭터 디자인 작업
- [ ] 마케팅 콘텐츠 제작
- [ ] 별도 AI 챗봇/RAG 서비스 구현
- [ ] 학교 이벤트, 커피차, 인스타 캠페인 실행 전략
- [ ] 대규모 인프라 이전 또는 관리형 DB 전환

## 5. Main Scenarios

### 시나리오 1: 사용자가 집중 시간을 기록하고 보상을 받는다

1. 사용자가 앱에서 일간 목표를 설정한다.
2. 사용자가 집중을 시작한다.
3. 서버는 집중 시작 상태와 기준 시간을 저장한다.
4. 사용자가 집중을 종료하거나 저장 요청을 보낸다.
5. 서버는 집중 시간, 경험치, 골드, 목표 달성 여부를 계산한다.
6. 서버는 중복 지급 없이 결과를 저장한다.
7. 사용자는 오늘의 집중 시간과 보상 결과를 확인한다.

### 시나리오 2: 주간 랭킹과 보상이 정산된다

1. Batch 서버가 정해진 기준 시각에 주간 랭킹 정산을 시작한다.
2. 서버는 랭킹 제외 대상과 참여 대상을 구분한다.
3. 서버는 티어, 승급, 유지, 강등, 보상 대상을 계산한다.
4. 서버는 중복 실행되어도 같은 보상이 두 번 지급되지 않도록 처리한다.
5. 사용자는 랭킹 화면 또는 우편함에서 결과를 확인한다.

### 시나리오 3: 운영자가 CS 요청을 처리한다

1. 운영자가 Admin 서버에 접근한다.
2. 운영자는 유저 ID, 닉네임, 학교, 신고, 재화 상태 등을 조회한다.
3. 필요한 경우 닉네임, 학교, 상태 메시지, 재화, 랭킹 경고, 길드 정보를 수정한다.
4. 서버는 권한을 확인하고 변경 결과를 저장한다.
5. 운영자는 처리 결과를 확인한다.

## 6. Server Requirements

### 멀티모듈

- API, Admin, Batch는 서로 직접 의존하지 않는다.
- 실행 가능한 모듈은 `levelup-application` 하위에 둔다.
- 공유 도메인은 `levelup-domain`, 기술 구현은 `levelup-infra`, 범용 코드는 `levelup-common`에 둔다.
- 각 모듈의 `bootJar`/`jar` 설정은 역할에 맞게 검증한다.

### API

- 모바일 앱에서 호출하는 사용자 기능을 담당한다.
- 인증/회원, 집중, 목표, 과목, Todo, 플래너, 캐릭터, 아이템, 랭킹, 길드, 결제, 우편함, 프로모션 API를 제공한다.
- 집중 시간 저장, 보상 지급, 결제 반영은 중복 요청을 고려한다.

### Admin

- 운영자와 CS 담당자가 사용하는 기능을 담당한다.
- 유저 조회, 재화 지급, 신고 확인, 랭킹 경고, 길드 정보 수정, 통계 조회 기능을 제공한다.
- 관리자 권한과 수동 처리 이력을 고려한다.

### Batch

- 시간 기반 정산과 집계를 담당한다.
- 랭킹 정산, 주간 보상, 통계 집계, 만료 처리를 수행한다.
- 중복 실행 방지와 재실행 가능성을 고려한다.

### Infra

- 현재는 단일 인스턴스 안에서 API blue-green, MySQL, Redis가 운영된다.
- 목표 구조에서는 API는 blue-green을 유지하고, Admin과 Batch는 독립 실행한다.
- Admin과 Batch는 API보다 낮은 가용성 요구사항을 가지며 짧은 다운타임을 감수할 수 있다.

## 7. Error And Edge Cases

- 같은 집중 저장 요청이 두 번 들어와도 경험치와 골드가 중복 지급되지 않아야 한다.
- 같은 보상 수령 요청이 반복되어도 보상이 한 번만 지급되어야 한다.
- RevenueCat webhook이 중복 전달되어도 구독 상태가 깨지지 않아야 한다.
- Batch가 중복 실행되어도 랭킹과 주간 보상이 중복 정산되지 않아야 한다.
- Admin 수동 지급과 자동 보상 지급이 충돌하지 않아야 한다.
- KST 기준 날짜와 주간 기준 시각이 기능별로 불명확하면 열린 질문으로 남긴다.

## 8. Acceptance Criteria

- [ ] `AGENTS.md`, `PROGRESS.md`, `ARCHITECTURE.md`, `DECISIONS.md`, `PRD.md`가 존재한다.
- [ ] API/Admin/Batch의 책임과 실행 단위가 문서화되어 있다.
- [ ] 현재 인프라 구조와 목표 인프라 구조가 문서화되어 있다.
- [ ] ECS 워크플로우가 현재 미사용 레거시임이 문서화되어 있다.
- [ ] 멀티모듈 의존성 점검 대상이 정리되어 있다.
- [ ] 집중 시간 저장 안정화가 다음 작업 후보로 명확히 정리되어 있다.
- [ ] 범위와 비범위가 분리되어 있어 AI 작업자가 임의로 범위를 넓히지 않는다.

## 9. Verification Plan

### 문서 검증

- `AGENTS.md`의 작업 시작 순서와 `PROGRESS.md`의 다음 작업 후보가 충돌하지 않는지 확인한다.
- `ARCHITECTURE.md`의 모듈 구조와 실제 `settings.gradle` 구성이 일치하는지 확인한다.
- `DECISIONS.md`의 결정 사항이 PRD의 범위와 충돌하지 않는지 확인한다.

### 코드/빌드 검증

- `./gradlew clean build`
- `./gradlew :levelup-application:api:test`
- `./gradlew :levelup-application:admin:test`
- `./gradlew :levelup-application:batch:test`

실행하지 못한 검증은 `PROGRESS.md`에 이유와 함께 기록한다.
