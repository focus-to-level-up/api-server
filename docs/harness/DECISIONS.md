# Decisions

마지막 갱신: 2026-06-22

## 목적

이 문서는 집중하면 레벨업 Spring Boot 서버 리뉴얼 과정에서 내려진 주요 의사결정과 이유를 기록한다.

---

## 2026-05-28 하네스 문서는 `.codex`와 `docs/harness`로 분리한다

### 문제

AI 작업 규칙과 프로젝트 기록을 같은 위치에 두면 문서의 목적이 흐려진다.

### 결정

`.codex`에는 agents, rules, skills를 두고, `docs/harness`에는 PRD, PROGRESS, ARCHITECTURE, DECISIONS를 둔다. 루트 `AGENTS.md`는 두 영역을 연결하는 입구 문서로 둔다.

### 이유

AI 운영 규칙과 서버 프로젝트 기록을 분리하면 문서의 책임이 선명해지고, 이후 수정 범위도 명확해진다.

---

## 2026-05-28 구현자와 리뷰어 페르소나를 분리한다

### 문제

분산락, 멱등성, 트랜잭션 같은 작업에서 여러 구현자가 같은 파일을 동시에 수정하면 충돌 가능성이 높다.

### 결정

직접 구현자는 `api-engineer`, `admin-engineer`, `batch-engineer`로 둔다. `integrity-reviewer`, `security-reviewer`, `qa-reviewer`, `devops-reviewer`는 리뷰와 체크를 담당한다.

### 이유

한 작업의 주 구현자를 한 명으로 두고, 품질 관점은 리뷰어가 검토하는 방식이 파일 충돌과 책임 혼선을 줄인다.

---

## 2026-05-28 API/Admin/Batch는 독립 실행 단위로 본다

### 문제

사용자 API, 관리자 기능, 배치 작업은 실행 시점과 가용성 요구사항이 다르다.

### 결정

`levelup-application:api`, `levelup-application:admin`, `levelup-application:batch`를 각각 독립 실행 가능한 Spring Boot 애플리케이션 모듈로 관리한다.

### 이유

API는 blue-green 배포로 다운타임을 최소화하고, Admin/Batch는 독립 실행하되 짧은 다운타임을 감수하는 구조가 현재 목표와 맞다.

---

## 2026-05-28 ECS 워크플로우는 미사용 레거시로 둔다

### 문제

GitHub Actions에 ECS 관련 워크플로우가 존재하지만 현재 활성 배포 전략으로 사용하지 않는다.

### 결정

ECS 워크플로우는 삭제하지 않고, 향후 ECS 또는 유사 배포 전략 검토용 레거시로 남겨둔다.

### 이유

현재 운영 방식과 혼동되지 않도록 활성 워크플로우와 구분하되, 향후 인프라 확장 시 참고할 수 있게 한다.

## 2026-05-28 리스크 관리는 Architecture 문서에서 분리한다

### 문제

`ARCHITECTURE.md`에 데이터 정합성, 장애 대응, 보상 중복 지급 같은 리스크를 길게 쓰면 구조 문서의 목적이 흐려진다.

### 결정

`ARCHITECTURE.md`는 모듈 구조, 의존성 방향, 인프라 구조 중심으로 유지한다. 리스크는 Notion 또는 별도 문서에서 관리한다.

### 이유

구조 문서와 리스크 문서를 분리하면 각 문서의 갱신 주기와 책임이 명확해진다.

## 2026-05-28 JWT는 API 모듈 내부에 유지한다

### 문제

JWT 구현은 Spring Security 필터, 사용자 인증 객체, 토큰 발급 흐름과 결합되어 있어 독립 infra 모듈로 분리하면 경계가 흐려진다.

### 결정

`levelup-infra:jwt` 모듈은 제거하고, JWT 발급/검증 코드는 `levelup-application:api` 내부에 유지한다.

### 이유

현재 JWT는 모바일 API 인증 흐름에 직접 붙어 있으므로 API-local로 두는 편이 의존성 방향과 작업 안정성에 맞다.

---

## 2026-06-09 Batch 기준 Clock은 Batch 모듈 내부에 둔다

### 문제

Batch Step들이 `Clock`을 주입받지만, 공통 모듈에 시간 설정을 두면 API/Admin까지 시간 정책 영향이 퍼질 수 있다.

### 결정

`Clock` Bean은 `levelup-application:batch` 내부에 두고 `Asia/Seoul` 기준으로 고정한다.

### 이유

랭킹, 보상, 통계 배치는 실행 애플리케이션의 기준 시각이 결과에 직접 영향을 주므로 Batch-local 설정이 가장 명확하다.

---

## 2026-06-09 Admin은 독립 계정과 세션 인증을 사용한다

### 문제

기존 Admin은 앱 회원 JWT와 `AdminWhitelist` 권한에 의존해 독립 운영과 Thymeleaf 전환에 적합하지 않다.

### 결정

Admin은 앱 회원과 연결되지 않은 `Admin` 아이디/비밀번호 계정을 사용하고, 역할 구분 없이 Spring Security 세션으로 인증한다.

### 이유

Admin 인증을 API JWT와 분리하면 배포와 보안 경계가 명확해지고 Thymeleaf 기반 운영 화면에 자연스럽게 적용할 수 있다.

---

## 2026-06-22 Batch 안정화는 CI/CD와 친구초대/출석 이후 필수 후속 과제로 진행한다

### 문제

Batch 보상, 통계, 리그/시즌 전환은 중간 장애와 재실행에 취약하지만, 지금 즉시 진행하면 멀티모듈 배포와 기능 연동 목표가 지연된다.

### 결정

현재 최우선 목표는 API/Admin/Batch 독립 CI/CD 구축, 친구초대 연동, 출석 연동으로 둔다. Batch 안정화는 이후 챗봇, 캐릭터 추가와 함께 병렬 후보 작업으로 진행한다.

### 이유

배포 파이프라인과 프론트 연동 기능이 먼저 완성되어야 리뉴얼 결과를 빠르게 검증할 수 있다. Batch 안정화는 운영 리스크가 큰 필수 작업이므로 후속 우선순위에서 누락되지 않게 별도 과제로 남긴다.
